## Общая часть команды

> Как меняется nDCG@10 на общем временном протоколе FAR-Trans при применении LLM для кодирования истории пользователя, представления активов и переранжирования фиксированного набора кандидатов — по сравнению с контрольным методом на каждом этапе?

Общие условия: 100 пользователей в том же порядке, 767 допустимых активов, отсечка 1 июня 2021 года, июньские покупки для оценки, повторы разрешены. Основное среднее nDCG@10 учитывает 89 пользователей с пустой truth как ноль. Второе среднее считают по 11 пользователям с покупками.

Пакет Алины с четырьмя baseline, протоколом и сохранёнными CBF-кандидатами описан в [заметке о сверке](TEAM5_PROTOCOL_CHECK.md). Обе Encoder-работы ранжируют весь допустимый каталог. Даша использует первые 20 из CBF50 для всех трёх Ranker-методов.

| Участница | Сравнение | nDCG@10 по всем 100 | nDCG@10 по 11 с покупками |
|---|---|---:|---:|
| Алина | Structured → Qwen для истории пользователя при одном user-kNN | 0.0436 → 0.0414 | 0.3963 → 0.3763 |
| Ульяна | TF-IDF → Qwen для представления активов при одном cosine scorer | 0.0225 → 0.0276 | 0.2043 → 0.2510 |
| Даша | LambdaMART / Qwen original ×3 / Qwen permutations ×3 на одном CBF20 | 0.0251 / 0.0184 / 0.0170 | 0.2278 / 0.1677 / 0.1544 |

У Даши обе ветки агрегировали по три реальных вызова Qwen на пользователя по одному правилу. При исходном порядке три ответа greedy decoding совпадали. Сравнение двух веток Qwen оценивает перестановки внутри Ranker. Сравнение с LambdaMART показывает качество LLM на том же CBF20.

В этих опытах Qwen улучшил представление активов. Для истории пользователя лучше сработал структурированный контроль, для переранжирования — LambdaMART. Выводы относятся к своим парам и условиям. Эффект полного Hybrid остаётся открытым вопросом.

## Мой эксперимент: сравнение представлений истории пользователя

1. Зафиксировать один список пользователей, cutoff и правила оценки из общего `protocol.json`.
2. Из прошлых покупок каждого пользователя подготовить одинаковый профиль доступных до cutoff категориальных полей актива. В HW7 рабочий набор полей: категория, подкатегория, сектор и индустрия; правила пропусков и конфликтов категорий нужно зафиксировать.
3. Построить контрольное структурированное представление и Qwen-представление из одного и того же профиля. Для Qwen записать точный model ID/revision, prompt/instruction, pooling/normalization, зависимости, precision и hardware.
4. Подать оба представления в один user-kNN scorer с одинаковой матрицей прошлых покупок, `k`, правилом tie-break, eligibility и fallback. Параметры выбрать на разрешённой validation-части или зафиксировать до теста; не подбирать по будущим покупкам оценочных пользователей.
5. Для обеих веток получить Top-10 из одного допустимого каталога и сохранить рекомендации, настройки и ошибки/пустые результаты.
6. Сопоставить структурированный encoder и Qwen encoder; отдельно включить четыре starter-baseline. Дополнительный TF-IDF-контроль можно добавить, если он использует те же пользовательские входы и не меняет scorer.
7. Проверить одного пользователя с будущими покупками: вручную сверить рекомендованные ISIN с июньской truth и пересчитать nDCG@10 по формуле из evaluator.

**Интерпретация:** разность Qwen − structured относится к замене представления в этом pipeline. Она не доказывает полезность инвестиционной рекомендации, прибыльность, причинный эффект или «понимание инвестора» моделью.

## Не путать с другими примерами

- Предложенный Ульяной личный дополнительный опыт TF-IDF против Qwen для поиска/кодирования активов относится к item-side retrieval. Это отдельный вопрос и не заменяет мой user-history Encoder.
- Starter extension имеет простой интерфейс перерасчёта весов истории для CBF; сам starter поясняет, что это не полноценный семантический embedding. Для эксперимента HW7 может понадобиться отдельный код, который принимает пользовательские векторы и использует их в user-kNN.
- Пример LLM Encoder из `llm-baselines` перефразирует описания активов и оценивает их TF-IDF CBF. Это полезный пример вызова модели и воспроизводимости, но не моя экспериментальная реализация.
- Не добавлять в основной вопрос сравнение с названиями активов или анализом знаний модели о будущем: обсуждение профессора с другой группой не меняет наш вопрос.
- Не запускать Hybrid только потому, что он изображён в лекционной схеме. В текущем HW8 достаточно одного законченного и проверенного вмешательства.

## Подтверждённая личная ручная проверка автора

Алина лично проверила в Colab пример пользователя `870E814DB274CFA95600`. Июньские Buy дают два уникальных relevant ISIN: `GRS014003032` и `GRS191213008`. В Top-10 Popularity они находятся на местах 3 и 10. Автор самостоятельно пересчитала:

```text
nDCG@10 = (1/log2(4) + 1/log2(11)) / (1 + 1/log2(3))
        = 0.48381288316677695
```

Результат совпал с Colab. Основание для атрибуции личного действия — сообщение автора в текущей OpenCode-сессии. Формулировка сверена с `hw8/outputs/colab/manual_truth_source_rows.json`, `manual_check.json`, `baseline/predictions.csv` и `baseline/per_user.csv`: два relevant ID, ранги и значение совпадают. Эта личная проверка автора отделена от предыдущих автоматических проверок агентов и не приписывается им. Проверка включена в индивидуальный отчёт.

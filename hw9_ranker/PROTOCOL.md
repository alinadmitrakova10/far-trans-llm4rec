# ДЗ9 · Протокол эксперимента Ranker

Дарья Бабикова, LLM4Rec, ВШЭ. FAR-Trans. Протокол зафиксирован до новых прогонов 26 ноября 2026 года. После начала прогонов любые отклонения записываются в раздел «Отклонения» в `DECISIONS.md` с датой и причиной. Зафиксированный протокол задним числом не изменяется.

## 2.1. Вопрос

Помогает ли zero-shot LLM-ранкер Qwen3-1.7B упорядочить фиксированный пул из 20 кандидатов лучше, чем исходный порядок пула и LambdaMART на том же пуле, когда пул собран из CBF, недавних покупок и популярности? LLM работает как Ranker и меняет только порядок кандидатов.

## 2.2. Оценочный срез

Development-срез FAR-Trans, отдельный от официального бенчмарка. Полный `protocol_hash` общего протокола стартера — `50efd4aeb415ba6f0c66dd0793a7c2033cdc32a42b86b58eebbca3e81eaf3417`. Берём ровно 100 warm-пользователей в порядке этого протокола, cutoff `2021-06-01`, метки из окна `[2021-06-01, 2021-07-01)`. Повторные покупки разрешены. Все методы используют одних и тех же пользователей, eligible-каталог и бинарные метки будущих покупок по правилам стартера.

## 2.3. Майское окно для выбора пула

Cutoff `2021-05-01`, 30 дней, окно `[2021-05-01, 2021-05-31)`. Первые 1000 warm-пользователей в детерминированном порядке `starter.select_users`: по `(SHA-256("42:" + user_id), user_id)`. Это срез майской валидации LambdaMART в ДЗ8. Пул выбирается только по маю, без июньских меток.

## 2.4. Правила пулов

У каждого пользователя целевой размер пула 20 уникальных eligible ISIN. Источники используют сведения строго до cutoff по правилам `vendor/far-trans/starter.py`. CBF — первые 50 результатов `order(content_scores(...))`. Popularity — полный порядок `order(popularity_scores(...))` по числу различных прошлых покупателей с разрешением равенств по ISIN. Recency — полный список eligible активов с прошлыми Buy-событиями пользователя, отсортированный по убыванию даты последней покупки, затем по ISIN. Sell в этом источнике не учитывается. Правила исключения дубликатов транзакций и реконструированных начальных позиций берутся из стартера. Исходный порядок пула задаёт matched control.

| Пул | Сборка |
| --- | --- |
| P0 | Первые 20 CBF50, как в ДЗ8. Справочный референс. |
| U1 | Последовательно recency, CBF, Popularity. |
| U2 | По одному новому ISIN за ход из CBF, recency, Popularity по кругу. Внутри хода пропускаем уже взятые ISIN до следующего нового. Исчерпанный источник пропускаем. |
| U3 | Первые 10 CBF, затем recency, затем Popularity. |

Добавляем только новые eligible ISIN, останавливаемся при 20. Если источники исчерпаны раньше, сохраняем фактическую длину и фиксируем короткий пул. Для top‑10 берём доступный префикс без дополнения.

## 2.5. Выбор пула

Для U1–U3 и справочно для P0 на майском срезе считаем число покрытых пар «пользователь–актив» из всех будущих пар, число покупателей хотя бы с одним попаданием из общего числа покупателей и потолок nDCG@10 при идеальной перестановке каждого пула. В потолке все попавшие в пул релевантные активы стоят первыми, а IDCG использует полную правду пользователя. Среднее считаем по всем и отдельно по покупателям.

Выбираем U1, U2 или U3 по максимальному абсолютному числу покрытых пар. При равенстве выбираем по числу покупателей с попаданием. При повторном равенстве приоритет `U1`, затем `U3`, затем `U2`. Потолок диагностический. Правило-победитель и основание выбора записываются в `DECISIONS.md` до любого июньского прогона на новом пуле.

### Кандидаты и признаки LambdaMART в ДЗ8

Пути к коду ДЗ8 ниже отсчитываются от `hw8/daria_babikova/hw2`.

- `scripts/build_temporal.py::main` вызывает `starter.select_users`, `starter.content_scores` и `starter.order`, берёт первые 20 CBF перед `input_contract.common_payload`. Для июньского входа `scripts/build_inputs.py::main` загружает сохранённый CBF20, созданный из префикса CBF50 в `scripts/build_candidates.py::main`. `scripts/evaluate_june.py::main` читает эти payload и соответствия кандидатов с ISIN, применяет замороженные преобразователь и Booster. Встроенный контроль ДЗ8 использует массив размером `100 × 20` и проверяет равенство с CBF стартера.
- `scripts/input_contract.py::common_payload` записывает `source_cbf_rank` как позицию в исходном CBF20, а `source_cbf_score` рассчитывает `cbf_scores` по всему eligible-каталогу. `feature_records` формирует признаки из позиции, балла CBF, возраста метаданных, истории покупок, давности последней покупки, профиля и категорий актива, сводки истории и взвешенных долей совпадений категорий. `scripts/ranker_features.py::structured_rows` добавляет индикаторы отсутствующих числовых значений и признаки отдельных позиций истории. `RankerFeatures.fit/transform` строит one-hot признаки и TF‑IDF по униграммам и биграммам названий кандидата и двух профилей истории, взвешенных по числу покупок и обратной давности. Сохраняются обе косинусные близости. Словари и TF‑IDF обучаются только на train.
- Для выбранного правила пересобираем пулы на всех трёх train-срезах, валидации и июне. Локальная позиция в новом пуле используется для matched control. Для LambdaMART `source_cbf_rank` означает настоящий ранг в CBF50, а для отсутствующего в CBF50 актива это `null`, который существующий энкодер кодирует значением `-1` и индикатором пропуска. `source_cbf_score` вычисляется для каждого кандидата по всему eligible-каталогу как в ДЗ8. Остальные признаки, метки и порядок строк внутри групп сохраняют прежнее определение. Пересчитываем размер групп, проверки целостности и исходный top‑10 по фактическим пулам. Убираем предположение `100 × 20` и проверку совпадения нового контроля с CBF. Разрешение равенств LambdaMART — по ISIN.

## 2.7. Абляция «чужая история»

Сортируем пользователей по `(число допустимых прошлых Buy-событий до cutoff, user_id)` по возрастанию. Счётчик берём из полной истории по правилам стартера. Делим на последовательные блоки по пять. Последний блок может быть короче, а блок из одного пользователя присоединяем к предыдущему. Для каждого seed `0`, `1`, `2` создаём отдельный `random.Random(seed)`. В порядке блоков перемешиваем свежую копию списка доноров блока этим генератором, пока перестановка не уберёт все неподвижные точки. Ставим доноров в соответствие получателям по позициям внутри блока.

Заменяем `history_rows` и `history_summary` донорскими. Сохраняем профиль, cutoff, пользователя, кандидатов, их признаки и порядок, а также параметры генерации. Чтобы строки кандидатов сохранялись побайтово, оставляем весь словарь коротких алиасов основного промпта получателя. Для нового донорского актива берём очередной неиспользованный короткий алиас в порядке сортировки канонических алиасов таких активов. Донорский актив, совпавший с активом из основного промпта, получает уже существующий алиас. Делаем 3 × 100 = 300 отдельных вызовов. Абляция проверяет использование явно переданной истории при фиксированном пуле, в котором сохраняются признаки кандидатов, рассчитанные по истории получателя.

## 2.8. Метрики

Основная метрика — макросреднее nDCG@10 по всем 100, для пустой правды оценка 0. Отдельно показываем макросреднее по покупателям и их число. Релевантность бинарная по уникальным eligible Buy-парам окна, IDCG учитывает будущие покупки вне пула. Показываем nDCG с четырьмя знаками, расчёты и сравнения выполняем до округления.

- Покрытие пула по парам и покупателям по п. 2.5.
- Среди 11 покупателей считаем «лучше / хуже / без изменений» для LLM против исходного порядка, LLM против LambdaMART, LambdaMART против исходного порядка, абляции против основного LLM. Равенство — `|Δ| ≤ 1e-12`. Для абляции основной итог сравнивает среднее nDCG каждого пользователя по трём сидам с его основной оценкой. Также показываем результаты по каждому сиду.
- Число пользователей с хотя бы одним релевантным попаданием в top‑10, отдельно из 100 и из 11. Число пользователей, чей упорядоченный top‑10 отличается от исходного порядка выбранного пула.
- Доля совпадающих по ISIN позиций top‑10 с Popularity при сравнении одинаковых рангов у одного пользователя. Знаменатель — 10 позиций у каждого пользователя, отсутствующие позиции считаются несовпадением.
- Невалидные ответы, repairs и fallback — число вызовов и число уникальных затронутых пользователей. Дополнительно nDCG@10 среди валидных ответов с их знаменателями, отдельно по всем валидным ответам и по валидным ответам покупателей. Для абляции даём эти условные показатели по каждому сиду.

## 2.9. Невалидный ответ

`scripts/llm_ranker.py::parse_response` применяет `strip()` и `json.loads`, требует ровно один JSON-массив из десяти различных строк, каждая из допустимых коротких алиасов кандидатов. Пояснения, ограждения Markdown, вложенные структуры, дубликаты и посторонние алиасы делают ответ невалидным. Repairs и повторные вызовы отсутствуют. `parse_or_fallback` переводит валидные короткие алиасы обратно в канонические, а при ошибке разбора возвращает первые 10 исходного порядка пула и ставит флаги `invalid` и `fallback`. При размере пула меньше 10 строгая валидность недостижима, применяется тот же fallback с фактическим префиксом. Пользователи с fallback участвуют в общих метриках. Переполнение контекста, OOM и ошибки бэкенда дают статус незавершённого прогона, как в `run_group` ДЗ8.

## 2.13. Отклонения
